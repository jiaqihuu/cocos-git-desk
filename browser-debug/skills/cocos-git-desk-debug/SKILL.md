# Runtime debugging with cocos-git-desk

Every tool comes from the single `cocos-git-desk` MCP (the same process as the Git tools, served by the running Creator). Precondition: Creator has the project open and the "Debug preview" panel is open; when a tool reports that the embedded preview is not connected or asks you to open the debug preview, ask the person to open or reload it in Creator (or call `creator_preview {action:"open"}`), do not start a browser yourself. Reading runtime state never authorizes running regressions, editing sources, changing back ends or sending real business requests.

## Nodes and properties (no observer needed)

- `runtime_inspector_hierarchy {contains?, activeOnly?, offset?, limit?}`: a page of the live node tree with `sessionId` and, per node, uuid/path/active/kind/scripts. Narrow with `contains` first; `truncated` and `scanLimitReached` mark coverage gaps.
- `runtime_inspector_inspect {uuid, sessionId, componentId?, all?}`: position/rotation/scale, prefab source, referenced assets, owning view and component fields, the same data as the runtime properties panel. A reloaded page rejects the old `sessionId`; query the hierarchy again.
- `runtime_inspector_layout {contains?, root?, activeOnly?, includeText?, limit?}`: flattened UI layout in design pixels with a top-left origin (as design tools measure), with anchor, scale, opacity, font size, color and sprite name. To compare with a design, hand the design boxes to `runtime_inspector_layout_compare {design:[...]}` and read the delta table instead of eyeballing screenshots.
- `runtime_inspector_select {uuid, sessionId}`: select the node in Creator's runtime hierarchy/properties panels and bring them forward so the person sees what you mean. `runtime_inspector_print {uuid, sessionId, componentId?}`: print the node or component to the Creator console and return the same record.

## View state, requests and exceptions (observer needed)

- When the task needs button/blocker state, a request timeline or exception locations, call `browser_debug_enable {}`; do not ask again for a task that is already authorized, and do not enable it for pure code edits or static checks. Read `preference` in `browser_debug_status` first: enabled and `applied` means query directly; `applied=false` means the page has not confirmed yet (usually the game has not finished starting or the preview is not connected). Turn it off with `browser_debug_disable` or `browser_debug_stop`; never change the person's choice at the end of a task, reload the page or perform business actions on your own.
- `browser_debug_hierarchy` / `browser_debug_inspect_node` read the project bridge's UI nodes with button/input-blocker state; text is opt-in (`includeText`), EditBox text is never returned, and coordinates do not prove that something is clickable.
- For performance questions sample `browser_debug_stats` several times (draw calls, triangles, fps). To see request contents call `browser_debug_capture_bodies {enabled:true}` (redacted, truncated at 4 KB; disable when done) and read `bodies` in `browser_debug_timeline`. An empty heartbeat reply is `empty`, not a failure.
- When the game is stuck use `browser_debug_state` for root UI layers and connection state; for request problems prefer `browser_debug_timeline` (pending, requestId, outcome, elapsedMs). `browser_debug_identity {compareDisk:true}` only when you suspect a change did not take effect; it compares a disk snapshot and does not prove the loaded modules or prefabs are current.
- Browser-side evidence: `browser_debug_start` captures console, exceptions, failed HTTP, WebSocket metadata and navigations; `browser_debug_events` / `summary` page through it, `mark` records reproduction steps, `compare` contrasts two intervals, `wait_for_reload` waits for a page reload. The timeline `sequence` and the events `id` are separate cursors; a changed sessionId resets them. gap/hasMore/truncated are coverage gaps, not "no problem".
- When asked to "record the problem" or "save the evidence", call `browser_debug_export` and report the directory; screenshots may contain personal data. An export is not an acceptance; on failure state clearly that the directory is incomplete or the session changed, and never stitch fragments of different pages into one package.

## Driving the game into a state (commands, per task authorization)

- To reproduce a view or a data condition, do not walk the person through clicks and do not guess from screenshots: `browser_debug_ui_list` lists registered views, `browser_debug_ui_open {name}` opens one (full prefab path when names collide), `ui_close` closes it; `browser_debug_language {code}` switches the language; `browser_debug_mock_set` returns a fake response for one RPC method or HTTP path (`fail` simulates a failure, `once` hits once, `delayMs` simulates a slow reply). Then read the result with `hierarchy` / `timeline`; the `command` and `mock-hit` entries in the timeline are the evidence of the reproduction.
- The commands that change state (`ui_open`, `ui_close`, `language` with `code`, `mock_set`) run only on the test environments listed in `bridge.testEnvironments` of `git-desk.config.json`; any other environment, or one the page does not report, is refused. When refused, switch the game to a test environment and reload the preview; do not work around it. When the preview toolbar shows active mock responses, some mocks are still registered.
- These commands change the game state in the preview and are only for reproductions or checks the current task authorizes; they never set accounts or login state, and the project bridge may exclude some requests (for example login) from mocking. Clear with `browser_debug_mock_clear` when done and say which results came from fake responses. The commands exist only in the preview; they do not represent release builds.

## Self-check before asking a person

- When a panel seems stale, a tool "does nothing" or code was just changed, call `runtime_inspector_status` first: it reports whether the preview is bound, whether the observer applies, the collector hub session and node count, which panels exist, what each panel currently renders (rows, names, selection, component blocks, messages) and recent failures; a panel absent from `reports` is closed or still running old code. Then read `creator_extension_log {level:["warn","error"]}` for the extension's own errors and notices. Only when neither explains the problem ask the person to reload or send a screenshot.

## Editor basics (no debug preview needed)

- `creator_asset_query` finds assets by uuid, db:// url, file path or name (optionally by type), so a prefab uuid or script name seen at runtime maps to a file; `creator_asset_open` opens scripts or opens prefabs/scenes in the scene editor, `creator_asset_reveal` highlights them in the assets panel.
- After a Git pull or merge, and before editing prefabs, call `creator_assets_refresh`; before touching the editor read `creator_editor_state` for unsaved tabs or prefab mode, and never save or discard for the person.
- After script changes run `creator_script_diagnostics` (a no-emit type check); it is a standing authorized check, not a runtime acceptance. When compile errors or import failures are unexplained read `creator_project_log {query:"error"}`.
- Whole-file edits of prefabs, scenes or JSON assets go through `creator_asset_write`, never through plain file tools: first put the path into a task with `git_desk_task_start` / `task_extend`, read the current `sha256` with `creator_asset_query`, then write with `taskId` and `expectedSha256` (`create:true` for new files); the tool validates the serialization and every `__uuid__` reference and refuses otherwise. Delete with `creator_asset_delete`, edit `.meta` with `creator_asset_meta`, and check `creator_asset_users` before changing a referenced asset. `creator_preview` reads the preview mode and URL; `action=open` opens the embedded debug preview that `browser_debug_*` / `runtime_inspector_*` need.
- Scene-editor changes (adding components, setting properties, instantiating prefabs) go `creator_scene_tree` -> `creator_node_inspect` -> `creator_property_set` / `creator_component_add` / `creator_node_create` / `creator_prefab_instantiate`, each with a `taskId` whose scope holds the open scene/prefab; the change stays in the editor until `creator_scene_save`, then verify related `.meta` with `git_desk_task_changes`. Review prefab/scene changes with `creator_prefab_diff {path}` (node, component and property level) rather than reading raw JSON; after adding, deleting or moving assets and before committing run `creator_meta_check` (`git_desk_commit_check` lists the same problems as blockers; do not bypass them). `creator_screenshot {panel:"scene"}` captures the editor, `creator_reload_extension` reloads the extension after rebuilding it, `creator_message` sends other read-only Creator messages (writes are refused).

Keep observed facts, code inferences and uncovered areas apart in reports. An HTTP/RPC completion is only the client-side result; streamed messages, the server's final state and device behaviour need separate evidence.

If the tools are not loaded, configure the MCP from Creator (Git Desk -> browser debugging -> configure AI clients; Claude Code uses `.mcp.json` at the project root, Codex `.codex/config.toml`), then reconnect the MCP or start a new session. Nobody needs to clone another repository or install Node.js.
